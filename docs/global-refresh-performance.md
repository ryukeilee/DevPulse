# 增量刷新性能对照

## 基线与瓶颈

基线是远端 `main` 的 `4a58cfa3fed3a123b4148917cddc3ece4249651b`。已有的工作树拓扑缓存、刷新内路径解析复用、Git 等待移出 Swift 协作线程池、扫描根书签并发、历史档案复用、相同快照副本解码复用和隐藏页面更新抑制均已在基线中。历史定位和实测见[刷新阶段 Git 执行](refresh-git-execution-performance.md)、[扫描根解析](scan-root-resolution-performance.md)、[共享快照提交](snapshot-commit-barrier-performance.md)及[页面切换](tab-performance.md)。

当前链路由 `ScanScheduler` 在主 actor 同步提交刷新起点快照，让 Widget 能显示刷新中状态。后台 `RefreshEngine` 解析已知扫描范围并运行各仓库的 Git 查询。完成处理回到主 actor 做仓库范围、身份和收藏派生，再由后台任务通过 `AppGroupStore` 进入 `SharedSnapshotStore` 提交最终快照。Widget 读取同一个存储实现，调度器按现有规则请求 timeline reload。

两处可直接消除的重复开销：

- `RepositoryIdentity` 为每次独立路径解析查询用户目录和沙盒目录。已有刷新内缓存只复用相同路径的结果，新路径仍重复查询相同的进程目录值。App 和 Widget 各自在首次使用时解析一次。路径存在性、符号链接和刷新间的路径可见性继续从文件系统取得。
- `SharedSnapshotStore` 生产写入格式化并排序 JSON；每次读取同一文件先解析协议头，再从头解析载荷。改用紧凑 JSON，一次解码中先检查版本与必填字段，再使用同一个 decoder 解码载荷。新旧格式使用同一组字段和版本号。提交后读取仍走完整校验与恢复选择。暂存回读、主备独立写入、锁、revision 比对、原子替换和同步屏障保留。

Git status 每轮仍检查所有可读仓库，未为减少命令次数引入工作树状态猜测。未改动刷新节奏、扫描范围、影响分析或通用备份模块。

## 测量范围

Apple M2（Mac14,2、8 核、16 GiB），macOS 27.2 (26B123)，Xcode 27.1 (27A9275)。基线和候选使用相同 Debug 配置，分别构建一次，随后交替先跑哪一版。测试宿主使用一次性 App Group 目录和偏好域。初次扫描和 Git fixture 创建不计入计时。

- 4 仓库使用原有合成 fixture，在两次扫描之间改动一个已跟踪文件，活动与历史档案需更新。
- 120 仓库使用同一组临时 Git 工作树，每个仓库有 100 个已提交文件，等量混合干净、已跟踪修改和未跟踪文件。测量中的 timer 刷新不再改动 fixture，活动与历史档案需保持原字节。目录列表仅传给测量脚本。
- 墙钟覆盖 timer 触发至快照成功落盘及档案检查。CPU 包含测试宿主及采集窗口中已退出的 Git 子进程。进程磁盘读写字节来自 `proc_pid_rusage`，只覆盖宿主归属的读写，并受系统缓存与分配粒度影响。宿主峰值物理占用覆盖测试进程生命周期，含 fixture 和首次扫描。文件字节数是逻辑大小。
- 主线程列是调度器记录的主 actor 同步阶段。Widget 列只记录最终同步阶段的 reload 请求，桌面 Widget 实际绘制及 SwiftUI 帧时间另无实测。

可使用已存在的 `scripts/measure-end-to-end-refresh.sh` 复跑。传入 `BASELINE_REV=4a58cfa`、`RUNS=9` 和独立的 `OUTPUT_DIR`；大集合模式再设置 `REAL_REPOSITORIES_FILE`。原始 `samples.tsv.raw` 保存主线程、磁盘、内存及最终快照指标。

每个场景 9 对。表中为各侧中位数，CPU 为累计 user + system 时间。仓库资料来自实际 Git 命令，性能数字适用于本机的隔离 fixture。

120 仓库整轮中位数下降 **16.4%**，9/9 对更快，配对中位差 −104.63 ms，配对 MAD 8.44 ms，双侧精确 sign test `p=0.00391`。CPU 中位数下降 **6.6%**，配对中位差 −113.49 ms，9/9 对更低。阶段下降主要出现在后台扫描准备（配对 −50.10 ms）、发现（−23.47 ms）和扫描完成处理（−7.79 ms）。Git 调用数与参数相同，status 耗时包含进程等待、调度和快照构造，不能据此归因到 Git 内部。

120 仓库的刷新起点反而更慢，配对中位差 +4.71 ms，9/9 对变慢。已检查测试宿主退出后的后续写入和落盘 revision，无法把起点变化归因到某次锁等待。已测的两个主 actor 阶段合计中位数为 37.63 → 33.83 ms，8/9 对缩短，未采样 SwiftUI 帧时间。四仓库整轮的配对中位差 +1.17 ms，配对 MAD 5.25 ms，只有 4/9 对更快，整体时延变化落在噪声内。两种规模的内存变化都未超出噪声，读字节结果仅代表这个热缓存负载。

120 仓库的墙钟配对差值（候选减基线，按采样顺序）为 −178.09、−98.60、−90.65、−104.63、−113.07、−91.80、−179.15、−99.40、−110.89 ms。四仓库对应 +6.10、−10.66、+2.86、−12.94、+4.79、−4.08、+14.62、+1.17、−5.11 ms。没有删除离群值。

### 存储层归因

`BENCH_REPOS='8 60 240' BENCH_RUNS=5 BENCH_ITERATIONS=15 ./scripts/benchmark-snapshot-persistence.sh --baseline-git 4a58cfa` 使用 `-O -whole-module-optimization` 单独对照存储。240 仓库稳态提交墙钟 20.12 → 17.90 ms、进程 CPU 11.21 → 9.10 ms，稳态读取 3.08 → 2.41 ms。60 仓库读取 1.44 → 1.22 ms，8 仓库稳态提交约 12.5 ms，两版接近。每个稳态提交仍写入两份独立载荷并执行三次强同步，每份不同内容只需一次 JSON 解析。33 个阶段与负载组合的规范化载荷指纹一致，15 个提交阶段的主备副本字节一致。

### 数据与故障验证

两个负载的 36 次计时刷新均通过既有仓库结果签名、成功状态、revision 和活动/历史档案检查。签名覆盖仓库名、分支、状态、各文件计数和收藏状态。载荷全字段对照由独立存储基准提供。

第一次大负载探针用两次无锁文件读取比对主备，基线也可撞到正在提交的后续快照。修正后在计时窗口外只取主文件大小，计时中的数据读取仍走带锁的存储入口。另行检查测试宿主退出后的落盘文件，36 个样本的主副本和备份都可解码，且两版都保留了成功结束状态。候选的三次退出发生在后续写入的主文件已前进、备份仍滞后一代的窗口。这与在主文件替换后中断的现有恢复协议一致，相关边界由故障注入覆盖。

定向测试通过 179 项（10 套）。完整验收通过 1,047 项（97 套）。WidgetKit 构建与接线检查 16 PASS、0 FAIL。故障注入覆盖主文件替换前后中断、提交点屏障失败、弱同步回落、损坏恢复及未来格式拒绝。跨进程套件验证旧 revision 无法覆盖新数据。独立审查两轮通过。测试使用未签名的隔离宿主，实机已注册 Widget 的显示和唤起时延未测。
