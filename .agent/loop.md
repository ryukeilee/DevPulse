# Maintenance Loop（证据驱动的维护循环）

本文件定义 DevPulse 的一次完整 Maintenance Loop。任何智能体进入本项目后，
如需进行「基于证据的现有功能维护」，只按本流程执行，不依赖额外口头说明。

一次 Loop = 一轮独立的问题调查与修复闭环，完整执行：

**Observe → Evidence → Decide → Execute → Verify → Record**

本文件之外仍需遵守的权威规则（优先级从高到低）：

- `AGENTS.md`（根目录，全局边界、测试映射、验证策略）
- `DevPulseNative/AGENTS.md`（产品级详细指南）
- `CLAUDE.md`（架构速览）
- `.agent/rules.md`（Loop 专属边界，本流程的精炼版）

---

## 0. 执行前（必读）

每次执行 Loop，必须先读取：

1. `.agent/rules.md`
2. `.agent/memory.md`
3. `.agent/history.md` 的最近 3~5 条记录

未完成上述读取前，禁止进入修改阶段。

---

## 1. Observe（观察）

只收集信息，**禁止修改代码**。按需并行执行：

- 当前工作区状态：`git status --porcelain=v2 --branch`
- 最近提交：`git log --oneline -15`
- 最近修改：`git status` 明细与 `git diff --stat`
- 测试状态：上次验证结果（见 `history.md` 最近记录）；如需确认编译基线，
  运行 `./scripts/verify.sh build`
- 已知问题：`history.md` 最近记录中的「剩余风险 / 待办」
- 用户反馈：本轮开始时用户给出的问题描述
- TODO/FIXME：`grep -rn "TODO\|FIXME" DevPulseNative/`（仅定位，不修改）
- 错误信息：构建/测试失败日志、运行时报错

产出：一份「候选问题清单」，每条附带**原始证据**（失败测试名、日志片段、
复现步骤、用户原话）。

---

## 2. Evidence（证据）

所有修改必须基于证据。**有效依据**：

- 可复现 Bug（有复现步骤）
- 测试失败（有失败测试名 / 日志）
- 明确行为异常（有预期对比）
- 用户反馈（有具体描述）
- 稳定性风险（崩溃、死锁、数据丢失、进程不退）
- 性能问题（有可量化基线对比）
- 测试缺口（有明确缺失的断言场景）

**无效依据**（不得作为修改理由）：

- 猜测、风格偏好
- 无复现的模糊担忧
- 「顺手改进」

没有足够证据 → **不修改**，结束本轮并记录。

---

## 3. Decide（决策）

每轮只选择**一个最高价值问题**。优先级（从上到下）：

1. 用户影响 Bug
2. 稳定性风险（崩溃 / 死锁 / 数据丢失 / 进程挂死）
3. 数据正确性风险
4. 性能问题
5. 错误处理问题
6. 测试缺口
7. 可维护性问题

必须避免：

- 重复处理 `history.md` 已标记完成的问题
- 纯代码风格调整（改命名、改排版、改格式）
- 没有验证方式的问题（无法构建 / 测试 / 观测）

若无高价值问题 → 结束本轮，记录「无变更」，**不要强行修改**。

---

## 4. Execute（执行）

只做解决该问题所需的最小必要修改：

- 小范围 diff（优先单文件 / 单一逻辑点）
- 保持现有架构（沿用现有类型、命名、数据流、验证模式）
- 保持兼容行为（不改变已公开行为、不破坏共享 snapshot 格式）
- 复用现有脚本与测试模式

禁止：

- 新增功能
- 大规模重构
- 无关优化
- 删除测试
- 修改测试来绕过问题
- 随意升级依赖
- 作为无关清理修改 bundle ID / entitlements / App Group / 签名等高风险项
  （若问题本身要求改动，必须显式验证并记录）

---

## 5. Verify（验证）

修改后必须验证。**禁止未验证宣布完成，禁止隐藏失败。**

本项目验证命令（从仓库根目录运行）：

```sh
# 一次性编译（同一会话首次，编译一次）
./scripts/verify.sh build

# 定向测试（复用已编译 bundle，秒级）——先跑最相关的测试类
./scripts/verify.sh test DevPulseTests/<AffectedTestClass>

# 全量验收（最终阶段才运行）
./scripts/verify.sh final

# 专项检查（如涉及 Widget 接线）
./scripts/verify.sh widgetkit
```

- 源码 ↔ 测试类映射表：见根 `AGENTS.md` 的「Targeted testing」一节
- 验证失败：基于**新的错误输出**继续修复，重复 Execute → Verify，
  直到通过或确认阻塞；不得仅靠延长超时掩盖问题
- 若某项行为无法在 CLI 验证（如已签名安装、运行时行为），在 Record 阶段
  如实标注「需手动确认」

---

## 6. Record（记录）

每轮 Loop 在 `.agent/history.md` 追加一条记录，字段：

| 字段 | 内容 |
|---|---|
| Loop 编号 | 连续递增 |
| 日期 | YYYY-MM-DD |
| 问题 | 一句话 |
| 证据 | 失败日志 / 复现 / 反馈原文摘录 |
| 原因 | 为何是最高价值问题 |
| 修改 | 文件 + diff 摘要 |
| 验证 | 实际运行过的命令与结果 |
| 剩余风险 | 未验证项 / 需手动确认项 |

`history.md` 维护规则：

- 保留最近 **20** 条记录
- 更早的记录**归档**到 `.agent/archive/`（剪切，不复制；命名规则见
  `archive/README.md`）
- 日常 Loop 不读取 archive，不污染上下文

---

## 结束条件

一轮 Loop 在以下任一情况下结束：

- Verify 完成且 Record 已更新
- Decide 判定无高价值问题（记录「无变更」）
- 阻塞（证据不足 / 外部依赖缺失）：在 Record 中写明阻塞原因、已验证内容与剩余风险
